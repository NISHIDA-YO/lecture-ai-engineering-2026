## 宿題(実装)

### やったこと：検索結果に前後ページの本文を付ける（`--neighbors` モード）

- ねらい：ページ単位の検索では、説明が前後のページに続いているときに根拠が欠ける。当たったページの前後も渡して補う
- 通常検索（`search` / `search_materials`）は変更せず、新しいモードとして追加したので変更前後を同じ条件で比べられる

| ファイル | 変更 |
|---|---|
| `app/config.py` | `NEIGHBOR_WINDOW = 1`（前後何ページ付けるか。0 で付けない） |
| `app/retrieval.py` | `search_with_neighbors(query)` を追加。`python -m app.retrieval --neighbors` で表示も可能 |
| `app/tools.py` | ツール `search_materials_with_neighbors` を追加（エラー処理は `search_materials` と同じ） |
| `app/agent.py` | 指示文 `NEIGHBORS_INSTRUCTIONS` と `--neighbors` モードを追加（Tree・Graph と同じく `override` で差し替え） |
| `tests/test_retrieval_neighbors.py` | API を呼ばないテスト 4 件（全 21 件 pass） |

処理の流れ（`search_with_neighbors`）

1. `search(query)` で上位 5 件を取得（従来どおり）
2. 各ヒットについて、同じ `document_id` の `page ± 1` を探す（資料をまたがない）
3. ヒット済み・追加済みのページは重複して返さない
4. 「前ページ → ヒット → 次ページ」の順に、検索順位の順で返す。各ページに `role`（hit / neighbor）、
   前後ページには `neighbor_of`（どのページの前後か）と `offset`（-1 / +1）を付ける
- 指示文には「前後ページは補足。質問の根拠になる内容があるときだけ使う」を追加

### 固定した条件

- モデル：`gemini-3.5-flash-lite`
- 対象資料：第1〜3回の本講義 214 ページ（同梱の検索DB、索引の再作成なし）
- 比較：通常検索（オプションなし）と `--neighbors` を同じ質問で実行

### 実行コマンド

```bash
export UV_ENV_FILE=.env
AIE_QUESTION='第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？'
AIE_QUESTION2='第3回の例では、コンパクションとセッションをまたぐメモリはどう違いますか。日々のメモはすべて長期メモリに入りますか'

uv run python -m app.retrieval --neighbors "LoRA QLoRA 違い"
uv run python -m app.agent --trace "$AIE_QUESTION"
uv run python -m app.agent --neighbors --trace "$AIE_QUESTION"
uv run python -m app.agent --trace "$AIE_QUESTION2"
uv run python -m app.agent --neighbors --trace "$AIE_QUESTION2"
```

`--neighbors`（質問：LoRAとQLoRAの違いは？）の記録

- ツール呼び出し：`search_materials_with_neighbors` 1回、検索語は「LoRA QLoRA 違い」（演習 STEP 2 と同じ検索語）
  - 返却の先頭は `lec02-main-p052`（hit 1位。p.51 も hit のため、前ページとしては付かない）
- 回答の要点：違いは「元の重みを圧縮するか」と「必要なメモリ量」
  - LoRA：元の重みは固定、細長い2つの小さな行列（低ランク）だけ学習（p.51・52）
  - QLoRA：LoRA＋元の重みを 4bit に量子化。メモリ約 1/4、Colab の 16GB GPU でも数十億パラメータ級を調整可能（p.52）
- 気づき
  - 回答に使われたのは p.51・52 だけで、どちらも hit のページ。前後ページ（neighbor）が引用された形跡はない
  - 通常検索（STEP 3）より入力 tokens が約 1.9 倍（3,028 → 5,649）。ただし質問文が違うので参考値
  - 「元の重みのデータ型はそのまま保持される（p.51）」は p.51 に明記がなく、モデルの補足。
    「Low-Rank Adaptation」「Quantized LoRA」の正式名称も資料になく、モデルの知識

| 方式 | 時間 | 入力 tokens | 出力 tokens | 応答回数 | 推定コスト | 取得ページ（hit / neighbor） | 引用ページ |

関係ページ（第3回）：p.13 メモリ／p.38 メモリがないと、毎回ゼロからやり直しになる／p.39 実装例：Claude／p.40 実装例：OpenClaw

| | 通常検索 | `--neighbors` |
|---|---|---|

| 期待根拠 p.13・39・40 | 3ページとも引用（＋p.38） | p.39・40 のみ。p.13 は引用なし |

- 分析
  - この質問では通常検索のほうが良い結果。期待する根拠 3 ページをすべて使い、両方の問いに直接答えた
  - `--neighbors` は入力 tokens が約 2 倍（2,500 → 4,880）なのに、引用は p.39・40 だけで p.13 が抜けた
  - ただし**検索語が違う**ため、差を前後ページの効果とは断定できない。モデルが検索語を毎回作るので、
    方式の差より検索語の揺れの影響が大きく出ている
  - 後半がヒントのみになったのは、指示文の「宿題の答えそのものは書かず、考え方のヒントで導く」による揺れ
    （演習の全文投入と同じ現象。両方の指示文に同じ一文がある）
  - p.39 が hit 1位なら、p.38・p.40 は前後ページとして自動で付く。`--neighbors` で p.40 が使えたのが
    hit 由来か neighbor 由来かは trace が省略表示のため未確認

#### 質問3：根拠が増えた例（根拠：第1回 p.39 → p.40）

質問：第1回の例題で、入力と出力の決め方を4通り挙げたあと、質問応答に決めた場合に次に考えることは何ですか？

  4候補を確認。クイズ（第2回 p.16→17、p.56→57）は答えページも hit したため除外。第1回 p.39→40、p.42→43 は

### 改善した例と、残る失敗・制約

- 改善した例：質問3。説明が次ページに続く場合、前後ページで根拠を補え、検索のやり直しが不要になった
- 質問1・2では改善なし（必要な根拠が通常検索の上位5件にすでに入っていた）
- 不要な情報が増えた例：質問1・2とも。質問2では前後ページ6件すべてが無関係
- 残る失敗：質問2で p.13 を取得したのに回答に使わなかった。関係の薄いページで根拠が埋もれた可能性があるが、
  検索語・回答方針（ヒントのみ）の揺れもあり1回では断定できない
- 制約：各条件1回のみ。モデルが検索語を毎回作るので、方式の差と揺れを分けきれない

### 気づき・疑問

- 前後ページが効くのは「説明が次ページに続くのに片方しか当たらない」場合だけ。スライドは1ページで完結しやすく、
  前後が章扉や別の話題になりやすい
- 改良案：同じ section 内だけで前後を付ける／距離が近い hit にだけ付ける／`read_page` をツール化して必要時だけ読ませる
- 取得方法の比較では、`app.retrieval` で検索語を固定した確認が欠かせない
